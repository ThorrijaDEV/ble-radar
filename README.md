# BLE Radar

A live terminal radar for the Bluetooth environment around you.

BLE Radar turns a BLE adapter into an instrument: it shows nearby
advertising devices as blips on a rotating radar sweep, tracks them across
time, records everything to SQLite, and lets you replay any recorded session
as if it were happening live.

## The problem

Walk into a room and ask "what Bluetooth devices are around me?" — the
answers are scattered across `bluetoothctl`, scanner UIs and logs. You get
raw MAC addresses, noisy RSSI values and no sense of what is *happening*:
which devices are new, which are fading away, how the environment changes
over time.

BLE Radar answers those questions in one screen, and stores every session so
nothing is lost.

## What it does

- **Live radar** — devices appear as blips with a rotating sweep; their
  position is deterministic per device, so you can recognize the same device
  when it comes back.
- **RSSI honesty** — blip *rings* are strength bands (strong / near / mid /
  far / weak), **not distance**. The UI says so. BLE provides no bearing
  information either, so angles are a stable visual convention.
- **Lifecycles** — devices appear as `NEW`, turn active, fade, and disappear
  when they stop advertising (`15s` quiet → fading, `30s` → gone).
- **Recording** — every radar run is stored in SQLite (sessions, devices,
  observations).
- **Replay** — `ble-radar replay latest` re-plays a recorded session on the
  radar at any speed, with seek (`--from +2m`) and pause.
- **Demo mode** — synthetic devices with realistic RSSI walks and lifecycles;
  deterministic with `--seed` (great for screenshots and CI).
- **Privacy** — raw addresses stay local; `export --sanitize` hashes them
  (SHA-256, 12 hex chars) and history/export never leak more than needed.

## Requirements

- Linux with BlueZ (systemd `bluetooth` service) — Arch: `bluetoothctl`,
  `btmgmt`, `btmon` come from `bluez-utils`
- A Bluetooth adapter supporting LE (the scan uses one long-lived D-Bus
  discovery session; don't run `busctl`/`dbus-send` helpers next to it, they
  kill the session — see `DESIGN.md` §3.2)
- Python 3.11+

## Installation

```sh
git clone https://github.com/ThorrijaDEV/ble-radar
cd ble-radar
python -m venv .venv
.venv/bin/pip install -e .        # or: pip install -e .[dev]  (for tests)
```

## Usage

```sh
ble-radar radar                 # live radar (full screen), records to the DB
ble-radar radar --backend demo  # same UI with synthetic devices
ble-radar radar --no-record     # look without storing
ble-radar record --duration 60  # headless recording session
ble-radar demo --seed 7         # synthetic demo, deterministic
ble-radar sessions              # list recorded sessions
ble-radar replay latest         # replay the newest session
ble-radar replay 3 --speed 8    # replay session 3 at 8x
ble-radar replay latest --from +2m   # start 2 minutes into the session
ble-radar history --device chip-tag  # observation history for one device
ble-radar export --sanitize -o data.json   # export with hashed addresses
ble-radar export --format csv --since 1h   # last hour as CSV
ble-radar status                # db stats + backend check
```

Keys in the radar: `q` quit, `p` pause, `+`/`-` replay speed, `d` addresses.

## Configuration

- Database: `~/.local/share/ble-radar/radar.db` (or `$XDG_DATA_HOME`), or
  set `BLE_RADAR_DB=/path/to/radar.db`, or pass `--db PATH`.
- Lifecycle windows are module constants in `ble_radar/lifecycle.py`
  (`ACTIVE_WINDOW=15`, `GONE_WINDOW=30`).

## Architecture

```text
scanners (bleak | demo | replay)
        │  Observation(address, rssi, seen_at, ...)
        ▼
RadarEngine ── per-device state machine + EMA smoothing
        │
        ▼
radar.py  (pure renderer: cells from snapshots + sweep)
        ▼
display.py (curses)          db.py (SQLite)
```

- `ble_radar/scan.py` — `Observation` + scanner protocol; demo and replay
  produce the same stream as real BLE.
- `ble_radar/backends.py` — bleak 3.x adapter on a dedicated asyncio thread.
- `ble_radar/engine.py` — ingestion, lifecycle, snapshots.
- `ble_radar/radar.py` — deterministic frame rendering (no I/O; unit-tested
  with golden frames).
- `ble_radar/replay.py` — timeline cursor that feeds past observations into
  the same engine.
- `ble_radar/db.py` — schema v1: `sessions`, `devices`, `observations`.
- `ble_radar/export.py` — JSON/CSV export with optional address hashing.

## Inspiration & attribution

Inspired by the family of BLE radar/visualizer experiments (btrpa-scan,
BTLEmap, Sonar-BLE-Radar, MetaRadar). This is an independent implementation —
no code was copied; the design borrows only ideas. Full research notes are in
`DESIGN.md` and `PROJECTS.md`:

- btrpa-scan — Apache-2.0 — concept: angle from address hash, RSSI→radius
- BTLEmap — Apache-2.0 — concept: honest RSSI ranking instead of distance
- Sonar-BLE-Radar — MIT — concept: terminal radar sweep
- MetaRadar — GPL-3.0 — concept: radar visualization

What's different here: one instrument for scan + record + replay + history,
device lifecycles with visual states, deterministic demo mode, sanitized
export, and a pure renderer that makes the UI testable.

## Honesty & privacy

- **RSSI ≠ distance.** Ring bands only; no distance claims anywhere.
- **Angles are not bearings.** They are a stable hash-derived layout.
- **Replay ≠ live.** The replay screen is labeled `REPLAY`.
- **Local-first.** The database never leaves your machine; export defaults to
  raw data and warns you to `--sanitize`.

## Limitations

- BLE address randomization can make one physical device look like several.
- The demo shows *advertising* devices only; connected devices may be silent.
- No bearing/distance estimation by design (see Honesty above).
